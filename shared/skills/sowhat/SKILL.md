# /sowhat — 伝え方を立て直す

​
ユーザーは、こちらのメッセージが伝わらないことに苛立っている。弁明せず、組み立て直して出し直す。
​
直前のメッセージの文面を手直ししない。見出しを付け替えたり説明を足したりしても、読み手の負担は変わらない。下の骨組みを、直前の文面を見ずに一から埋める。
​

## 手順

​

1. `/Users/yoshitogoto/dotfiles/shared/refs/communication.md` を読む。**毎回読む。記憶で代用しない**
2. ユーザーの最後の発言を読み直し、何を聞かれているか・何を求められているかを1文にする。直前のメッセージが別の問いに答えていたら、ユーザーの問いのほうに答える。言葉を技術の話に読み替えていないかも確かめる(「認可のついでに」が「認可のMRで一緒に」なのか「認可の仕組みで」なのか)
3. 種別を決め、下の「骨組み」のどれかを選ぶ
4. 骨組みを埋める。直前のメッセージより短くする
5. 下の点検項目に照らす
6. 送る。1行目は結論にし、「前のメッセージは〜でした」「書き直します」のような前置きや反省を書かない
7. 以後このセッションの全メッセージで、読んだ型に従い続ける
​

## 骨組み

​

### 事実を聞かれたことへの返事

​
「〜は対応中?」「〜はどうなっている?」のように、事実を聞かれただけのとき。1行目で問いに答える。理由や根拠は2文まで。見出しは付けない。
​
返事に推奨や、ユーザーに決めてもらうことが入るなら、この骨組みではなく下の「相談・不具合の説明」を使う。「〜した方がいい気がする」「〜でいいのでは」は意見を求められているので相談にあたる。
​
<example>
まだ対応していません。認可のMRの最新のコミットにも、パスワードを伏せる変更は入っていません。
</example>
​

### 相談・不具合の説明

​
見出しをこの順に並べる。各見出しの下は2〜4文か、短いリストにする。
​

```
## 結論
何を推奨するかを1〜2文。最後に、答えてほしいことを疑問文で1つ。
## ゴール
本来どうあるべきか。
## 現状
今どうなっているか。事実だけ。
## 課題
ゴールと現状のずれで、具体的にどのケースで何が困るか。
## 対応案
案①(推奨)、案②…をネストしたリストで。
## 評価
判断軸ごとに案を比べた表。列見出しは「案①：別のMRで伏せる」のように名前まで書く。表の下に、推奨する理由を1〜2文。
```

## 結論

​
パスワードが平文で見えている3か所は、認可のMRに入れず、別のMRで直すことを推奨します。この進め方でよいかを答えてください。

## ゴール

​
閲覧専用の利用者を含め、誰にもFTP受信のパスワードが平文で見えない状態にする。画面はこれまでどおり使えるままにする。
​

## 現状

​

- 設定ファイル管理のAPIが、パスワードを含む設定ファイルを中身のまま返す
- 認可のMRは、どのロールがどのAPIを呼べるかを決めるもので、APIが返す中身は変えない
​

## 課題

​
認可でできるのは、APIを呼べなくすることだけです。認可で塞ぐと、閲覧専用の利用者は設定ファイル管理の画面を使えなくなります。
​

## 対応案

​

- 案①：別のMRで伏せる
  - APIが返す値のうちパスワードを伏せ字にする
- 案②：認可で塞ぐ
  - パスワードを返すAPIを、閲覧専用の利用者には呼べなくする
​

## 評価

​

| 判断軸 | 案①：別のMRで伏せる | 案②：認可で塞ぐ |
| --- | --- | --- |
| 閲覧専用の画面 | 使える | 使えない |
| 着手できる時期 | 今 | 認可のMRの後 |
​
画面を使えるまま見えなくできるのは案①だけなので、案①を推奨します。

</example>

## 点検項目
​
同じ項目の写しを `/Users/yoshitogoto/dotfiles/claude/hooks/sowhat-nudge.py` が毎ターン差し込んでいる。ここを変えたらそちらも合わせる。
​
- [ ] それだけ読んで意味がわかるか(前の会話・サブエージェントの報告・作業経過に依存していないか)
- [ ] ユーザーに何をしてほしいかがわかるか(読むだけ/チェック/判断/回答)
- [ ] 共有・報告・相談・確認・質問のどれなのかが伝わるか。ただし無理に当てはめていないか(聞かれたことへの返事に【共有】等のずれたラベルをつけていないか)
- [ ] その種別の「書かないこと」を書いていないか(途中経過、弁明、判断の丸投げ、推測)
- [ ] 書き方が情報の構造から導出されているか(リスト/番号/チェックボックス/見出し/表)
- [ ] 表が狭いペインでも表のまま出る幅か(セルにURL・文を入れていないか。URLと説明は表の下に書く)
- [ ] 「見出し語: 数文の説明」をリストで並べていないか(つながった話は段落の文章で書く)
- [ ] ファイルの場所は絶対パスか。MR・Issueは名前とブラウザで開けるフルURLがセットか
- [ ] 用語を初出で説明しているか。造語・内輪の呼び名を使っていないか
- [ ] 結論が先頭にあるか。リード文の数行だけで何が言いたいか分かり、推奨する案が案の一覧より前に1行で書いてあるか
- [ ] 事実・解釈・提案を1つの文に混ぜていないか。推奨は「〜を推奨する」と書き、事実と同じ言い切りにしていないか
- [ ] 読み手の認知負荷を削ったか。書き直すたびに長くしていないか、頼まれていない説明を足していないか、判断の依頼を1つに絞ったか。返事を待っていることを「返事を待っているのは1つだけです」のような件数や指さしで済ませず、聞きたいことそのものをその場に書いたか
- [ ] 「- 見出し語: 説明」の1行詰めや「ゴール:」のようなラベル行が無いか。ネストか見出しにしたか
- [ ] 文や項目の末尾に括弧書きの補足を足していないか
- [ ] 日本語の文に半角スペースを混ぜていないか。見出しや項目名の区切りは全角コロン「：」か
- [ ] 案に記号を振り、評価表の列見出しにも同じ記号を書いたか。推奨順があるなら案①②、順番が無いなら案A・B
- [ ] 評価表に○△×を使わず、案どうしで比べられる語句・数値で書いたか
- [ ] 使用禁止語を使っていないか。結線・効く・箱・筋・段・推す、文書の版数の意味の「版」、サーバーへ置く意味の「配布」。英語を直訳した日本語も使わない

## やらないこと
​
- 直前のメッセージを書き直さずに謝る
- 何が欠けていたかを冒頭で述べる(反省文になり、結論が2行目以降に下がる)
- 直前の文面を下敷きにして手直しする
- なぜそう書いたかの説明を足す(ユーザーはそれを読みたくない)
- 種別を宣言しただけで中身が同じもの出す
- ユーザーが答えていない質問を、同じ文面で繰り返す(伝わらなかったのはこちらの書き方なので、聞き方を変える)
